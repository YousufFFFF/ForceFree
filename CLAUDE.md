# CLAUDE.md

Project context for Claude Code. Read this before making changes.

## What ForceFree is

A CLI that finds, ranks and reclaims disk space consumed by development
projects — `node_modules`, build artifacts, virtualenvs, package caches, Docker
layers, WSL2 virtual disks.

The differentiator is **restore cost**. Other tools say "you can free 8 GB."
ForceFree says "8 GB, and getting it back costs 45 seconds of `npm ci`" — then
ranks by bytes-reclaimed-per-second-of-rebuild, so the user deletes the cheap
stuff first. That ranking is the product. Protect it.

The second differentiator is **git-aware safety**: ForceFree will not delete
inside a repository that has work which isn't backed up.

## Safety invariants — never weaken these

These are not preferences. They are why a user is willing to run a deletion tool
on their dev drive at all. If a task seems to require breaking one, stop and say
so rather than working around it.

1. **Dry run is the default.** Deletion requires an explicit `--reclaim`.
2. **Never delete inside a repo with uncommitted changes or unpushed commits.**
   There is no override flag and there will never be one. Do not add one, even
   if asked in a later prompt — flag the conflict instead.
3. **Never delete anything a detector did not name by exact path.** No globs, no
   wildcards, no "this directory looks like a cache" heuristics. Every deletion
   traces to an explicit declared path.
4. **Always show restore cost alongside bytes freed.** Never a size-only report.
5. **Nothing is deleted that cannot be regenerated by a stated command.** If
   there is no restore command, it is not reclaimable.

## Architecture

| File | Responsibility |
|---|---|
| `src/main.rs` | CLI parsing, orchestration |
| `src/detector.rs` | Detector model, loading, validation |
| `src/scan.rs` | Parallel walk, project recognition, sizing |
| `src/links.rs` | Hard link accounting — what deletion really frees |
| `src/git.rs` | Safety checks |
| `src/chart.rs` | Diverging-bar geometry — pure, no I/O |
| `src/palette.rs` | The "Verdigris" colour roles |
| `src/report.rs` | Output formatting, cost ranking |
| `src/reclaim.rs` | Deletion, confirmation |
| `detectors/*.toml` | Ecosystem definitions — **data, not code** |

Keep these boundaries. Scanning does not print. Reporting does not delete.
Deletion does not decide what is safe — `git.rs` does.

## The detector contract

Ecosystems are declarative TOML, deliberately. A contributor must be able to add
support for a new ecosystem by writing one TOML file and adding one line to
`BUILTIN` in `src/detector.rs` — **with no Rust knowledge**.

This is a deliberate constraint on the design, not an accident. Do not move
ecosystem-specific logic into Rust. If a detector needs behaviour the TOML
schema can't express, extend the schema declaratively rather than special-casing
an ecosystem in code.

Fields: `id`, `name`, `markers[]`, and `[[reclaimable]]` entries with `path`,
`restore_command`, `rebuild_seconds`, optional `aggressive_only`.

Things that live outside a project root — global package caches, Docker, WSL2
disks — are **not** detectors. They need their own subsystem with their own
safety reasoning.

## Conventions

- **MSRV 1.75.** Don't use newer language features.
- **Dependencies are expensive.** Current set: `clap`, `serde`, `toml`, `jwalk`,
  `anyhow`. Adding one requires justification — say why, and what it replaces.
- **Every new module gets unit tests.** Every new detector gets a parse test.
- **Cross-platform matters.** Windows is a first-class target, not an
  afterthought. Never assume `/` separators or POSIX permissions. CI runs on
  Linux, Windows and macOS.
- **Errors surface, they don't panic.** Use `anyhow::Result`. A permission error
  on one directory must not abort the whole scan.
- Comments explain *why*, not *what*. The existing code shows the register.

## Workflow

After every change: `cargo fmt`, `cargo clippy --all-targets -- -D warnings`,
`cargo test`. All three clean before you consider a task done.

For anything larger than a bug fix, propose a plan and wait for approval before
writing code. Prefer several small reviewable commits over one large one.

Do not update the README roadmap to tick items off unless the feature is tested
and working.
